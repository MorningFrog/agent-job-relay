# Automated testing and evidence

[Documentation index](README.md) · [Contributing](../CONTRIBUTING.md) · [Implementation status](IMPLEMENTATION_STATUS.md)

For reader-facing installation and ChatGPT Desktop acceptance steps, use [manual testing](manual-testing.md). This guide covers developer verification. Tests keep state, fake endpoints and logs under repository-local `.tmp/`; they do not modify personal settings, services, unrelated application state or real ChatGPT Desktop endpoints.

## Required checks

Run from the repository root:

```bash
npm ci --prefix web --ignore-scripts --no-audit --no-fund
npm test --prefix web
npm run build --prefix web
cargo fmt --check
cargo clippy --all-targets -- -D warnings
cargo test --all-targets
cargo build --release --locked
```

Current counts, toolchains and results are maintained in [implementation status](IMPLEMENTATION_STATUS.md). [Woodpecker CI](ci.md) defines Rust 1.89 minimum-version compilation, pinned stable Linux/Windows native gates and installed development-package checks. The full four-workflow graph has successful exact-head PR and independent main Push Server evidence; current acceptance is tracked in the implementation status. Legacy macOS portable-test checks remain in the unavailable Actions reference configuration. The [macOS ARM64 cross-build/native adapter](macos-arm64.md) is an explicitly untested development path, not replacement test evidence; no tests are run for that change. Current manual release preparation/publication uses the route in the [release guide](release.md). A configured workflow alone does not establish successful server execution or native OS support.

Development notes stay under `## [Unreleased]`; validate synchronized versions with `python3 scripts/release_actions.py source --allow-unreleased`. Local/CI package checks use `prepare_release.py --allow-unreleased`, which marks the packages as development-only. For formal local preparation, `python3 scripts/finalize_release.py --version <unused-x.y.z>` synchronizes release versions/pins, then runs frontend/native/release-flow/online-maintenance gates before automatically finalizing the notes; see [requirements and expected result](release.md#prepare-and-review) and the [script index](../scripts/README.md). Actions still requires committed dated notes and refuses development-only promotion. Release fixtures cover version/pin synchronization before gates, untouched dependency locks/private web metadata, preserved launcher modes/line endings, invalid/public-version refusal before edits, failed-gate and interrupted-replacement retry, successful ordering, failure preservation, repeated dates, malformed/duplicate/empty notes, partial publication, source changes and inventory refusal without real publication.

## Test selection and artifacts

Test behavior, correctness and regression risk through the existing Rust suites and fake hosts. Preserve the legacy daemon fixture and other required reference data. Do not add tests for README wording/structure or other implementation details that have no product-interface contract. Review documentation changes directly as part of normal maintenance.

Keep generated test state, outputs, reports and logs under ignored repository-local `.tmp/` or `target/`; never commit them. Versioned documentation records concise current results and verification limits. Historical runs are available in Git history, while required test cases/fixtures stay tracked.

The four configuration-integration fixtures run serially within their test binary. This prevents a parallel CLI fork from briefly inheriting another fixture's configuration lock before exec; each case keeps its own isolated paths and all assertions. Runtime concurrency cases continue to exercise their existing explicit concurrent workloads.

Plugin update/repair preservation checks checkpoint committed WAL pages before comparing complete database hashes. Terminal state and daemon-lock release can precede the last pooled connection closing; checkpoint timing alone must not look like data loss. The interrupted-repair fixture seeds committed WAL history before taking its snapshot and verifies that record remains readable after repair, alongside the existing backup/journal and database-preservation assertions.

Online-maintenance fixtures use bounded status checks before operations that require a running or completed job. CLI `wait` returns on any new event, including `started`, so its successful response is not completion evidence. A file-controlled workload covers this distinction and active-update refusal before completion; guard readiness failures include the child exit status and stderr. Run `cargo test --test online_update` to verify the five cases without changing real installations or profiles.

Node navigation tests cover fragment consumption, repeated selection, credential refresh and listener cleanup; actual host navigation is a separate browser check.
