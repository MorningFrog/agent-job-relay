# Local and MCP protocols (v0.1)

[Documentation index](README.md) · [Command reference](commands.md) · [Architecture](architecture.md)

## IPC

Linux owner-only Unix socket `<state>/relay.sock`; same effective UID required. Runtime IPC has no TCP listener; the separately authenticated loopback Web API is described below. One request and response per connection, 4-byte little-endian unsigned length followed by UTF-8 JSON. Request cap 128 KiB, response cap 1 MiB; 5-second framing deadline, at most 32 simultaneous connections. Client deadline 40 seconds; event wait 1–30 seconds. Unsupported versions fail explicitly.

Request: `{"protocol_version":1,"request":{"op":"doctor"}}`. Response: `{"protocol_version":1,"ok":true,"result":{...}}` or an error string. `agent-job-relay request '{"op":"doctor"}'` wraps the envelope for you.

Requests are the serde-tagged enum in src/ipc.rs. `start` takes a `spec` containing `command` (`{"kind":"exec","program":"...","args":[]}` or explicit `{"kind":"shell","interpreter":"sh","script":"..."}`), absolute `cwd`, optional `env`, `timeout_seconds`, registration key `session`, `idempotency_key`. No implicit shell. Full inherited environment is not serialized. Explicit env values ARE persisted in the private DB; status omits them.

Runtime 0.1.12+ supports IPC v1 `start_batch {specs:[StartSpec,...]}` and Doctor `batch_submission=true`, without a storage migration. Envelopes require 1–16 specs, distinct required 1–128-byte idempotency keys and at most 128 KiB including the IPC wrapper. Envelope/type/key errors reject before admission. Semantic validation, key conflicts and quota failures are per-item errors; each new item uses the existing independent transaction and eight-active-job quota. Results preserve input order as `{accepted,rejected,results:[{index,idempotency_key,accepted,result:{job,wake}} | {index,idempotency_key,accepted:false,error}]}`. Counts include identical existing jobs as accepted. Retrying unchanged keys/specs returns committed Job/Run IDs and attempts uncommitted/rejected items; no batch-wide rollback, reservation or scheduler exists. See [batch usage](usage.md#submit-independent-commands-together-0112) for interruption, partial-admission and caller-replacement semantics.

Lists return at most 100 rows and `next_cursor`; pass it as `after`. Job/session/ delivery cursors use SQLite rowid, event cursors use monotonic event sequence. Log cursors are byte offsets; reads cap at 64 KiB and return lossy UTF-8 text, `bytes`, `next_cursor`, `untrusted`, `cap_bytes`. Do not use text length as offset. Original bytes remain in capped files. `wait` returns any events after cursor, terminal state or deadline, so a `started` event may return before completion.

## External command variants (0.1.12+)

`StartSpec.command` also accepts `remote {remote:{target_id,transport:{program,args},intent}}` and `github_actions {workflow:{repository,run_id,attempt,hostname?,gh_program?}}`, with `kind` as the discriminator. Remote intent is `launch {spec:StartSpec}` or `attach {run:{job_id,run_id,attempt},allow_stop:false}`; nested external commands are rejected. The outer cwd/session identify the observer/caller; the inner launch spec supplies remote cwd/env/timeout/native rules. CLI `start-spec --file` and existing MCP start/batch share validation and require Doctor `remote_execution`/`github_actions_observation` capabilities before submission. No new MCP tool or SQLite migration is needed; old binaries cannot deserialize external specs.

`remote init` explicitly provisions a stable profile UUID. `remote serve` implements one bounded stdio JSON exchange with version/target/request echoes, native launch idempotency and run-fenced lookup/sample/stop. This protocol is separate from local length-prefixed IPC. Limits, schemas and adapter obligations are in [remote execution](remote-execution.md#adapter-contract-v1). Raw remote byte cursors use persisted local log lengths; original mappings, samples and event cursors live in existing archived/backed-up runtime observations. Restore still orphans execution intents and never replays them. The remote provisioning UUID is not part of a restored profile.

## Structured progress (0.1.12+)

Doctor advertises `structured_progress_v1=true`. Native runner stdout/stderr accept bounded newline-delimited `AJR_PROGRESS` v1 samples as untrusted data; `monitor_rules.condition.kind=progress` adds a source, stage/step/metric trigger and cooldown_seconds. Existing inspect responses include durable source high-water marks, latest values, counters and milestones under `observation.progress`; bounded `progress` events and terminal `payload.progress` retain evidence. CLI/MCP/Web use the same structures, revisions and Outbox transaction. No new wire version, tool, execution callback or schema migration is introduced. Exact framing, deduplication, quotas and terminal behavior are in [the progress contract](progress.md).

## MCP

Official rmcp 3.7 stdio server, pure stdout protocol and stderr diagnostics, 128 KiB bounded input lines. Legacy initialize/initialized uses negotiated capabilities; protocol 2026-07-28 uses server/discover and per-request client metadata without initialize. Both input paths have protocol-fixture coverage; actual host form UI remains separate. Tools derive their argument schemas from the same Request types as IPC:

`job_goal_consent`, `job_goal_wait` (experimental), `job_inspect`, `job_monitor`, `job_start`, `job_start_batch` (0.1.12+), `job_status`, `job_list`, `job_logs`, `job_events`, `job_stop`, `job_wait`, `job_doctor`, `job_connect_session`, `job_register_session`, `job_sessions`, `job_inbox`, `job_probe_session`, `job_recover_session`, `job_invalidate_session`, `job_add_wake_target`, `job_rebind_target`, `job_deliveries`, `job_retry_delivery`, `job_delivery_attempts`.

`job_start_batch` takes `specs` plus optional current-caller `binding`, `wake_me` and `full`. Binding supplies every item's session and missing cwd, rejecting any conflicting explicit session before submission. Shared mode constrains wake_me to false; dedicated inherited-context `wake_me=true` or CLI `start-batch --wake` registers/probes once and binds all items. These convenience fields do not enter raw IPC. The batch client requires the explicit Doctor capability before any item submission; it never silently expands the batch against an old daemon. Mixed or all-item rejection returns ordinary MCP content with indexed errors, while envelope/preflight errors use isError. Compact output applies the ordinary start view to each successful result.

`job_start` retains `{"spec":{...}}` and also accepts `{"binding":{"session_key":"<key>","cwd":"<absolute-directory>"},"spec":{"command":{...}}}`. The binding comes from the actual host caller and supplies missing cwd/session fields; conflicting explicit session identities fail before submission. `job_recover_session` accepts the same binding instead of repeating session_key. The server never stores or guesses a shared caller context. Every MCP tool accepts optional `full=true`; common job/doctor/recovery results otherwise use compact views with stable IDs, outcomes, cursors and next steps. These convenience fields are stripped before unchanged IPC v1 requests; raw IPC is unaffected. Register arguments remain `{"registration":{...}}`. Tool execution failures use isError content so the Agent can read the diagnosis. No MCP Tasks or subscriptions are advertised. No session ID is fabricated from MCP connection identity.

## Task titles (unreleased source)

`StartSpec.title` is an optional 1–80-character Unicode string with no surrounding whitespace or control characters, accepted by single/batch CLI, IPC and MCP submission. Full Job records, inspection summaries and compact MCP job views retain supplied titles. The title is stored inside the existing JSON specification and included in its idempotency comparison/hash; changing it under a used key conflicts. Omitted titles serialize exactly as before, and older Job snapshots deserialize with no title, preserving hot/cold retries without a schema migration. The schema stays v12, IPC stays v1 and the tool catalog stays at 25; use matching updated runtime entries, since older binaries reject the new field.

## Delivery

Completion + stable Event ID + unique `(event_id,target_id)` Outbox rows commit in one IMMEDIATE SQLite transaction. One daemon dispatcher permits four concurrent attempts across chats and claims durable work for 10 seconds; transport deadline is 3 seconds. Transactional claims allow only one live attempt per adapter/agent/host/logical session, even across registration instances, and select ready records in insertion order. Waiting retries do not block newer ready records. Empty queues use read-only checks; local writes wake the workers, with idle fallback checks backing off from 100 ms to one second for independent-process changes. Old claim tokens cannot ack a new claim. Interrupted attempts are recorded on reclaim. TTL is 24 hours from the original event. Temporary errors retry until TTL, using finite exponential backoff with jitter capped at five minutes including jitter. Identity/lease failures wait in retry_wait with failure_kind=rebind_required until explicit recovery or expiry; unsupported capabilities/malformed catalogs dead-letter immediately. Delivery queries expose failure_kind and next_attempt_at (Unix milliseconds). There is no five-failure cutoff. Explicit retry renews TTL and keeps the delivery ID/history; it does not rerun the command.

States: pending, leased, retry_wait, dead_letter, cancelled, notification_recorded (local inbox only), accepted_by_host (ChatGPT Desktop or public plugin-host admission). No adapter proves confirmed_resumed, and that state cannot be manually faked.

Inbox notifications use stable ID filenames and atomic replacement. ChatGPT Desktop uses the observed private tools/list and tools/call wire format in an isolated adapter, capability preflight, callerSource=codex, explicit caller and destination thread IDs, stable callId and no fallback. Socket inode/ctime fingerprint and lease bind registration to a host endpoint instance. Re-register explicitly after host restart; rebind targets when host instance/session identity changes. Already transmitted requests cannot be revoked by rebind. Receivers must dedupe stable delivery IDs: private host dedupe is not proven.

## Client convenience (no wire-version change)

`start --wake` and, for dedicated per-session MCP, `job_start` with `wake_me: true` opt into experimental ChatGPT Desktop wake. The client reads its current inherited host context, auto-starts its per-state daemon if absent/refused, registers/refreshes and probes, then detects an active Desktop goal before submission. Ordinary work retains the exact session key; an active goal requires the automatically prepared wait binding and internal goal admission instead. `wake_me` is not part of the raw IPC start payload. Do not combine it with explicit spec.session. `job_connect_session` accepts only the optional `full` view flag and performs the same connection probe without starting a workload; CLI workspace binding uses `connect`; legacy `session connect` remains a registration-only operation.

Missing context or capability fails before execution; no latest-session or notification-only fallback is selected. MCP needs a dedicated per-session host context; otherwise use CLI from the Agent's current ChatGPT Desktop terminal tool. Automatic leases last 24 hours, refreshed on each opted-in submission. New host fingerprints create distinct registrations; existing targets remain unchanged.

Client submissions and explicit registrations auto-launch a daemon; current source also replaces an older daemon under the startup lock with pinned-peer shutdown, migration checks and readiness/version verification. Equal/newer daemons are reused. Doctor/status queries do not start or replace daemons. Raw IPC `{"op":"shutdown"}` / CLI `daemon stop` stops this daemon and retains runners and data; it is not advertised as an MCP tool. Repeating stop is a client-side no-op when the socket is already unavailable.

## Installed/shared MCP binding (no wire-version change)

Generated plugin and setup entries use `mcp --shared-host`. This rejects MCP `wake_me=true` and `job_connect_session` before submitting any workload, even if the process inherited another valid chat's environment. The start schema marks wake_me as const false in this mode. Server instructions advertise a terminal binding command as explicit argv. Both native and online plugins run `connect --cwd <project>` in the calling chat's terminal and pass its `binding` object. The compatible `session connect --brief` and explicit spec.session/cwd workflow remains available. Brief responses contain session_key, binding (session_key/cwd), probe=passed, can_resume and can_confirm_resume, without a host endpoint or raw registration. Neither users nor a shared process invent thread IDs.

CLI doctor can report a stopped daemon without creating state. Its optional `--check-mcp` runs a five-second bounded private initialize/discovery/EOF check, with bounded frames and required tool-schema checks. It reports a stdio self-check, not actual host connectivity or wake. A real MCP `job_doctor` call reports that the request reached the server and describes its binding mode; no host message or capability probe is sent. Configuration ownership checks remain separate.

## Loaded-image readiness (additive Doctor fields, IPC v1)

Current Linux Doctor reports `runner_launch_from_loaded_image=true` when its mapped image is available via the procfs self-executable link. The IPC client adds `daemon_executable_path_available` from the actual connected peer's procfs image pathname, if accessible. Missing evidence is not fabricated. A removed path plus absence of the new capability identifies the affected legacy daemon; submission fails before creating a job. CLI Doctor adds `runner_readiness` with status `restart_required` and idle-restart guidance. It does not restart the daemon. Neither field is a claim of new code being loaded or Agent continuation.

The local Codex bundle uses `.codex-plugin/plugin.json` + `.mcp.json` and an absolute stable installation command. Actual CLI loader discovery (25 tools on Codex 0.164.0), standalone stdio self-check, host `job_doctor`, job execution and live wake remain separate evidence levels. Portable source templates are not installed. Offline bundle/bootstrap/update and explicit cache status/refresh are CLI management operations; they add no MCP tools or IPC/schema version. Cached launchers use the same managed native image as MCP (ADR 0007).

## Legacy shutdown compatibility (0.1.2 client)

Early v0.1.0 daemons use IPC v1 but reject the later `shutdown` operation. The client preserves the responding same-UID peer PID and boot/start identity inside a typed remote error. Only that specific unknown-operation error activates legacy shutdown: recheck the original peer and healthy v0.1.0 Doctor, recognize the native daemon executable/arguments, open a Linux pidfd, signal SIGINT and await exit. Other errors, changed identities and unrecognized peers are not signalled. The response reports `daemon=stopped`, `method=legacy_sigint` and data preservation. No new operation/version is required in the old daemon; no MCP shutdown tool is introduced. All successful stops now wait for daemon-lock release. Installation profile selection is CLI-only (`daemon stop --install-root`), not a job caller identity or a state migration. PID/name matching alone cannot authorize a signal.

## Explicit same-chat recovery (schema v6, additive IPC v1 operation)

`connect --recover [--apply] [--after N --limit 20]` (compatible entry: `session recover`) refreshes/probes the current terminal binding and invokes `recover_session {session_key,apply,after,limit}`. MCP exposes job_recover_session; shared MCP requires the fresh caller binding or its explicit session_key. Preview registers/probes, but does not change targets/deliveries or send a host message. The daemon probes the supplied registration and fences concurrent changes inside the recovery transaction. Matching requires agent/logical/host and identical ChatGPT Desktop caller/destination. No unrelated-session endpoint scan occurs.

Active jobs and unresolved unexpired events may move to a new immutable target; original delivery IDs, attempts and event TTL survive. Accepted/expired events are not replayed. Live claims on either old/new target are skipped, stale claims are fenced and their unfinished attempts are recorded. Existing canonical target deliveries are coalesced with a superseded-by audit; accepted canonical deliveries are never reset. Target/delivery changes and target_recoveries audit commit in one transaction. The response includes recent audits and bounded target pagination. Low-level target rebind/replay remains an explicit advanced API with its existing semantics; this conservative recovery operation does not renew expired TTLs.

## Long-job lease renewal (0.1.3)

Registration optionally sets renew_on_delivery=true (default false for old/manual records). Automatic terminal bindings opt in. Only an owned ChatGPT Desktop registration with identical caller/destination may enable it; inbox is excluded. When an actual delivery claim has a lease expiring within one hour, the dispatcher probes the original endpoint fingerprint/owner and tools/list capability, including when the session lease already expired during a long job. There is no periodic host scan. The existing three-second attempt deadline includes this optional probe.

Before extending the session by its configured lease duration, a transaction rechecks the unchanged registration/expiry, connected flag and active target with the current unexpired claim token. Renewal and its audit commit together. The original delivery ID and event TTL remain unchanged. Changed/invalidated endpoints never renew automatically; concurrent refresh retries from the new snapshot. The probe provides endpoint/capability evidence, not Agent execution confirmation. Doctor exposes same_chat_recovery and delivery_time_renewal capability flags; automatic binding verifies these capabilities before registration/job mutation, after current-source version handover has selected an equal/newer daemon. Published clients still need an explicit same-profile stop/update. Manual opted-out registration omits the new false field for older wire compatibility. Schema v6 is unchanged.

## Public plugin bridge (source 0.1.8)

A `plugin_bridge` registration uses an explicit owned endpoint, identical caller/destination and experimental opt-in. The core pins the endpoint fingerprint and same-user peer, then sends one length-prefixed JSON-RPC request per connection: `relay/probe` or `relay/deliver`, with `protocol_version=1`, `agent_kind`, `session_id`, `caller_session_id`, `instance_id` and `host_id`. Delivery adds only stable `delivery_id`, `event_id`, `job_id` and terminal `kind`. No command/output is included. Responses cap at 16 KiB within three seconds.

A result echoes protocol/agent/session/instance/host and `can_resume=true`; delivery also requires `accepted=true` and matching delivery/event/job IDs. Errors do not route to another adapter. An accepted result does not prove a model ran. Opted-in renewal and explicit scoped recovery reuse the existing transaction/audit/claim fences, matching the exact adapter discriminator. Doctor advertises `plugin_bridge=true`. IPC v1/SQLite v6 stay unchanged, but older executables do not understand the new adapter records; they must not be used to operate this profile.

OpenCode V1 injects a fresh binding from the host tool context into shared MCP. Claude's scaffold provides an inbox key from explicit skill session substitution; it advertises no auto-resume. Host packages and verification boundaries are in [host plugins](host-plugins.md).

## Windows daemon startup diagnostics

Doctor adds `daemon_launch_method` (`windows_native`, `windows_cim`, `unix_native` or `foreground`). CLI Windows diagnostics include the current `AJR_WINDOWS_STARTUP` policy and a literal-quoted same-profile `outside_terminal_command`. These are diagnostic fields, not job/session identities or proof of host continuation. The internal random startup pipe transfers bounded version/environment/cwd data only after mutual process/image/SID/integrity and private-DACL validation; it is not a public workload execution API. See [ADR 0012](adr/0012-windows-on-demand-bootstrap.md). SQLite v6 and public IPC v1 remain unchanged.

## Automatic data maintenance (schema v9)

The new CLI-only `data` commands add no MCP tools or IPC operation/version changes. Existing bounded status/list/events/deliveries/attempts/inbox/log operations include cold history. Stable cursor high-water marks prevent reuse after hot-row removal; idempotency spans both tiers. Explicit delivery/target mutations restore terminal relational history atomically without launching workloads. Doctor's store result establishes connection/schema health; `store_check` names that scope and `capacity` reports maintenance health. `data check` runs explicit SQLite integrity/foreign-key checks. Schema v9 requires stopping old daemons and finishing old active runs before migration. Backup manifests and cold snapshots have independent format version 1. See [data maintenance](data-maintenance.md).

## Runtime monitoring and Web UI (0.1.10 and newer)

IPC v1 adds inspect (optional job_id/before/limit), monitor (job_id plus optional tagged mutation) and private ui_info. MCP exposes job_inspect/job_monitor within the current 25-tool catalog; ui_info/shutdown remain CLI/private-IPC operations. StartSpec.monitor_rules defaults to an omitted empty vector, preserving old canonical idempotency bytes. A rule has condition no_output/elapsed/contains, action alert/stop, optional notify_agent and grace_seconds (default 5). Update/enable/remove require expected_revision. Rules are bounded to 16 identities and 128 revisions each per job and trigger once per revision. Inspect returns compact paginated overview records or a bounded detailed snapshot with raw byte counts, a rolling 64-KiB tail per stream, application revisions and newest events. Stop accepts grace_seconds (0–300) and wait_seconds (0–30), returns existing job fields plus stop_outcome, and never revises an existing terminal result.

Monitor triggers insert ordinary monitor_alert events with stable IDs and atomically record trigger/reason/optional stop intent/outbox entries. Notification payloads remain metadata-only. Unresolved alerts become cancelled and expired claims are fenced; live claims retain per-chat exclusion until transport completion when a terminal result supersedes them; records, expiry and attempt history remain intact. Existing accepted/leased effects cannot be recalled. OpenCode's bridge accepts monitor_alert; real-host running-alert admission still needs qualification. All output/evidence remains untrusted data.

Source 0.1.16 adds an informational `feedback` object to start results, accepted batch items and detailed inspect snapshots, including compact MCP responses. It summarizes persisted rules/application/source evidence and active recorded target capabilities; it never probes hosts, creates bindings or changes delivery state. Terminal archived detail derives the same receipt from its single validated snapshot without rehydration. Diagnostics failure after admission returns `feedback.status=unknown` while retaining the admitted Job/Run. See [receipt fields/statuses](progress.md#choose-and-verify-feedback-before-yielding). No StartSpec, schema, IPC version or tool-count change is required.

Each daemon normally binds a random 127.0.0.1 HTTP port. ui_info returns an ephemeral fragment access URL over authenticated private IPC; doctor exposes only availability/base URL. The browser converts the fragment to a session-scoped bearer header and removes it from visible navigation. POST /api/request admits only inspection/rule/stop/history/doctor requests, with a 128-KiB body bound and 16 request slots. GET /api/events uses authenticated SSE snapshots with eight viewers and one queued update per viewer. Assets are embedded React/Vite output, with Host/Origin validation and restrictive CSP; no CORS or remote binding is enabled. AJR_WEB_UI=off is the explicit startup opt-out. See [runtime monitoring](runtime-monitoring.md).

## Scoped consent and goal waiting (schema v12)

CLI `connect --request-label <label> --job-count <1..16>` detects the actual active goal and returns `status=needs_confirmation`, `session_key` and `consent`, without a wait/job/binding. `job_goal_consent {request_id,session_key,decision:ask,expected_revision?}` claims one question. Negotiated legacy form support uses `elicitation/create`; protocol 2026-07-28 returns `InputRequiredResult` with server-held opaque `requestState` and request-keyed `inputRequests`. The retry must echo that state and exactly one matching `inputResponses` entry; only `action=accept` with `content.allow_goal_pause=true` approves. Native question tokens cannot be overridden by an Agent assertion. Without form support, return `ask_user_now=true` once; later calls return pending state. `decision=allow/decline` records only an actual host-question reply with `expected_revision`; `revoke` closes future admission/control, not execution. `authorization_source` distinguishes native confirmation from cooperative Agent/terminal assertions.

Schema v11 stores consent snapshots/audits and an optional consent reference on waits; v12 adds selected feedback event/delivery IDs, cycle count and last-restoration time. Pending scope lasts ten minutes, claimed input five minutes, approved admission 24 hours; the fixed job budget is consumed atomically with original admission. Repeated pending preparation does not extend expiry. Approved scope is reused only through `connect --request-id`, never silently adopted by a new request. Responses expose remaining budget and bounded original Job/Run/wait identities. Deleted/replaced goals, changed callers/controllers, revocation and restore invalidate future controls; jobs are not replayed or stopped. Supported v8–v12 backups restore forward into new profiles with consent/control fences.

An inactive original goal returns `status=goal_not_active` and `goal_status` without a submission binding. A blocked/budget-limited/otherwise inactive original goal retains unexpired consent, revision, budget and member IDs; native confirmation cannot prompt or approve until it is active. Host Resume permits reconnection with the same request ID, without another approved-consent question. Controller/read errors fail closed without invalidating consent or cancelling waits; decline/revocation needs no controller access. Observation-triggered invalidation is revision-fenced against concurrent decisions. Goal completion/deletion/replacement and existing expiry/revocation/restore fences remain terminal for that request; no inactive status is automatically overwritten.

`goal_wait {goal_wait_id,cancel:false,confirm_paused:false,expected_revision?}` remains public IPC/MCP; cancel/confirmation are exclusive and revision-fenced. Scoped reconnection prepares the original controller/goal/registration, then MCP start/batch uses hidden `start_goal`/`start_goal_batch`. Accepted membership freezes in `sealed` with `host_pause_required=true`. Only successful originating-host native pause followed by confirmation can enter `waiting`; missing acknowledgement expires after five minutes. All original runs must finish before final status-only restoration and one merged notification. Source 0.1.17 notifying monitor rules can temporarily restore the same goal for an intermediate report: the selected event/delivery and cycle are returned in feedback, host_pause_required remains true, and the Agent must natively pause and confirm that revision before returning to waiting. Intermediate acceptance does not set the final notification flag. Group limits are 32 cycles, a 60-second minimum interval and a five-minute re-pause deadline; final completion supersedes feedback before transmission, or follows its re-pause if already transmitted. Uncertain mutation acknowledgements are never replayed. General recovery cannot move pinned groups. Single-handoff `--wait-goal` compatibility remains under actual user permission.

Doctor reports `scoped_goal_consent=true`, `goal_wait_host_pause=true`, `goal_wait_feedback=true`, `automatic_goal_pause_supported=false` and `goal_pause_authorization_policy=ask_once_per_request`. MCP adds negotiated `native_goal_consent_form`, `managed_mcp_updates_supported` and `runtime_workflow_sha256`. There are 25 source tools. Host generation/CAS is unavailable; source assertions are not independent attestation. See [operation and limits](goal-waiting.md).

## Runtime workflow and retained MCP updates

`instructions` reads the current workflow/policy/digest without daemon/job admission. Cached skills and MCP initialization use stable launcher/profile instructions. Managed MCP verifies the original installation and forwards current calls/catalogs under shared locks, preserving negotiated protocol/capabilities, input responses and opaque request state. Worker initialization/discovery, correlation, 128-KiB requests, 1-MiB frames and supervised cleanup are bounded. Transport has 90 seconds of active budget; one native human question may add up to 300 seconds, with a 390-second total bound. Legacy input holds the installation read lock; modern input-required returns and releases it before the answer. Changed image identity emits one catalog notice. Cancellation/uncertain transmission never replays. Historical entries need one migration/reconnection. See [ADR 0019](adr/0019-current-runtime-workflows.md).

## Unreleased result diagnostics and log retention

Detailed inspection adds read-only `notifications`: aggregate delivery `counts`, independent `completion` counts, `latest_problem`, derived `status`, compact current `goal`, host-scoped original-caller `recovery` instructions (Desktop argv, OpenCode tool or inbox inspection) and `agent_execution=unconfirmed`. Counts include all hot/cold deliveries, independently from the first 20 delivery records. Derivation never probes a host, changes claims or infers Agent execution. MCP `job_inspect` defaults to bounded excerpts/progress/notification diagnostics, three event excerpts and evidence cursors (`recent_events_after` for omitted retained detail, `events_after` for later events); `full=true` preserves the complete snapshot. CLI opts in with `inspect --compact`; raw IPC/HTTP detail remains complete.

Native stream prefixes stay at absolute bytes `[0,16777216)`. New output after the prefix uses four 1-MiB slots in `stdout.recent`/`stderr.recent`, with 64-byte per-slot v1 headers: `AJRLOG01`, little-endian absolute start/length, SHA-256 and eight reserved zero bytes. The fixed file bound is 4 MiB + 256 bytes. Replacement synchronizes header invalidation before overwriting bytes, then synchronizes data and the new header; shared/exclusive file locks fence readers and backup copies. Zero headers denote unavailable slots; malformed headers/ranges/checksums fail explicitly. Full segments publish during capture and the final partial segment at normal drain; pending output still has the separately sampled live tail.

Existing `logs` responses add `cursor`, `retained_ranges`, `gaps`, `retained_end`, `skipped` and `recent_cap_bytes`. `next_cursor` remains an absolute byte offset; a missing interval is explicitly skipped before returning at most the requested bytes from one contiguous retained range. Legacy prefix cursors are unchanged. Text is UTF-8-lossy, while native storage retains raw bytes. CLI/Web export bounds reads to the first observed retained end and marks missing intervals. Remote v1 raw-byte copying continues using its original prefix-only contract. Gzip archives and format-1 backup manifests now also carry the exact managed `.recent`/`.recent.gz` names; older backups remain readable. Schema v12, IPC v1 and 25 MCP tools remain unchanged.
