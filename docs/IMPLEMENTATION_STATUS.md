## Implemented behavior

| Area | Current behavior |
|---|---|
| Native execution | Explicit argv/shell, validated cwd/env/timeout, typed Job/Run states with unchanged SQL/JSON vocabulary, durable original IDs/attempt, unchanged-key idempotency, independent runner/process groups/Windows Job Objects, live-Linux adopted-child cleanup, flushed/synchronized logs, conservative orphan handling and no execution replay |
| Batch | 1–16 independent specs with distinct keys, indexed partial admission and safe retries; eight execution slots per profile; persisted deadlines (24 hours by default, explicit no-wait override) admit up to 64 extra waiting jobs, preserving FIFO launch reservations and independent rules/stop/notifications |
| Scoped goal consent | Structured `needs_confirmation` before wait/job creation and one negotiated MCP or Agent question. Default approval covers later rounds of the original request and Goal without a job-count limit or deadline. Bounded approvals retain their recorded scope and jobs are counted transactionally. Host Resume reuses the request, controller read loss retains consent/waits, withdrawal works offline and restore fences old consent |
| Goal handoff | Originating native pause plus revision-fenced confirmation before `waiting`; current source also requires the original Desktop host to report no active submitting/reporting turn before restoration. Submissions/register operations start the selected daemon on demand. Doctor/status do not. Windows daemon-only CIM bootstrap authenticates both endpoints and avoids services/elevation; runners still require native breakaway. Configuration/marketplace writes are individually atomic, not a cross-file transaction. Rust 1.89 all-target compilation is verified on Linux; native behavior gates use stable Rust separately.
Runtime 0.1.20 CLI/MCP/Web search spans hot and validated archived records with bounded scan cursors, status/directory/time filters and read-only stopped-profile access. See [inspection/search](runtime-monitoring.md) and [disk policy](data-maintenance.md).

## Release and support boundaries

Use [release preparation](release.md#prepare-and-review) to finalize Unreleased changes into an unused version before building a new candidate. Each Actions candidate retains its original run and commit identity. Release All coordinates preview and, when explicitly selected, stages for maintainer npm 2FA, finalizes GitHub and invokes independent Check Release. Retain published notes, dates, tags, exact bytes and receipts. Formal Linux payloads must pass startup and SQLite checks on glibc **2.34**. Earlier provider candidates and receipts remain bound to their original runs.

Goal wake-up and usually successful pause/resume have user-reported sustained-use evidence, with the fast-completion guard retained and the reported 0.1.26 native-envelope rejection corrected in source; installed real-host fix acceptance remains open. Other resume failures and the separate blocked-state report remain undiagnosed. Windows goal/controller, direct native confirmation UI, a specifically observed full real-model three-round workflow, goal intermediate feedback/native re-pause, changed-host goal handling and measured long-duration savings need separate qualification. Host goal generation/CAS is unavailable. Actual results completed while Desktop is closed, receiver deduplication and multi-day renewal remain open. Claude account-backed loading, OpenCode real-provider/V2, stronger containment, disk-loss qualification and cross-file install recovery remain in [TODO](TODO.md). No adapter automatically records `confirmed_resumed`.
