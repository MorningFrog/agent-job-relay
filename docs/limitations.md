# Current limitations

[Documentation index](README.md) · [Features and support](features.md) · [Security](security.md)

## Platforms and host capabilities

- Linux and Windows x86_64 have verified native runtimes. Windows native launch needs breakaway; a cleanup job can use the verified same-user local CIM daemon bootstrap. Policies denying PowerShell/CIM, restricted tokens and provider limits can require an external-terminal fallback. Windows ChatGPT Desktop same-chat continuation is verified with Full access; restricted terminal binding can fail with access denied and single-command authorization remains unverified. macOS instance identity/lifecycle remain unimplemented. Native Windows CI/release checks passed for the published baseline; each new candidate requires its own native/package gates.

- Codex CLI integration provides MCP tools plus a durable notification inbox. It does not start/resume an Agent automatically. No turn writer is owned by this program. Experimental Desktop goal waiting uses only bounded public goal-state RPCs; no authentication or model invocation is performed by the controller.

- ChatGPT Desktop transport is opt-in, private and experimental. v0.1.8 is verified with ChatGPT Desktop on Linux and Windows, including same-chat continuation after task completion. Additional host versions, results completed while the host is closed, real multi-day renewal and receiver deduplication remain separate qualifications. An ack remains accepted_by_host; no adapter automatically confirms resume. See [live verification](live-e2e.md).

- Runtime 0.1.12+ [scoped goal waiting](goal-waiting.md) obtains one actual user answer before admission, then requires originating native pause and revision-fenced acknowledgement. The user confirms local automatic pause after approval. Direct native-form UI, full real-model multi-round restoration and Windows goal/controller remain unqualified. Cooperative Agent/terminal assertions are not independent host attestation. Storage-only pause cannot notify Desktop’s cached goal. Missing goal generation/CAS leaves identical same-second replacement and final verification/write/send races; deleted goals are never recreated. Existing turns/child Agents are not interrupted, changed hosts need manual goal handling and cancellation cannot recall transmitted effects.

- Explicit host/session identities are supplied by the trusted caller. The private API cannot independently attest them. Socket fingerprint/lease changes require refresh or rebind; no magical historical conversation discovery.

Host packages require >=0.1.6 core (Windows OpenCode requires >=0.1.7); OpenCode npm candidates depend on the matching packaged runtime, while Claude still requires separate development setup; Codex offline export does not package them. Older executables cannot interpret plugin_bridge records despite unchanged SQLite v6. OpenCode uses public prompt admission with bounded in-process dedupe, not persistent exactly-once delivery or automatic confirmation of model execution. It must explicitly rebind after bridge replacement. Claude wake remains unavailable; no guessed resume command, private ChatGPT Desktop fallback, hooks or channels are shipped. See [host plugins](host-plugins.md).

## Caller binding and notification delivery

Convenience support: `start --wake` / MCP wake_me=true remove manual registration when current host context is inherited. They cannot infer identity in an ordinary terminal or shared MCP process. Use the current ChatGPT Desktop Agent terminal tool when MCP lacks those variables. Automatic sessions lease for 24 hours and opt into delivery-time renewal after probing the same endpoint fingerprint/owner/capability. No periodic host polling is added. Changed endpoints or invalidation need explicit same-chat recovery; manual/legacy registrations default to no renewal. Real multi-day expiry remains unverified; automated expiry tests use fault injection.

Installed/generated MCP uses shared-host mode and an explicit caller binding for spec.session; binding objects also supply the captured workspace, with full=true for complete MCP diagnostic records. ChatGPT Desktop obtains it from the current terminal, while OpenCode uses actual tool context. Live acceptance covers the published baseline rather than every later API convenience change; see [live evidence](live-e2e.md). A local terminal is required; cloud chats without one cannot bind.

- At-least-once delivery: a host may execute a request even if ack is lost. Stable IDs are provided; host deduplication is not proven. Rebind cancels future claims, not effects already transmitted externally.

## Execution lifetime and containment

- Job attempt=1. Idempotent submission returns the original job; it does not rerun failure. Use a new key/job for a deliberate rerun. Ambiguous launches become orphaned after a 5-second grace period and are never auto-replayed.

- Runner writes terminal state directly to SQLite while daemon is absent. Lost runner lock means orphaned, not success. Runtime 0.1.14 provides bounded cleanup of a live Linux runner's adopted descendants, including session escapes, through parent-verified pidfds. SIGKILL/power loss cannot run Rust cleanup; Linux parent-death kills the direct workload, but descendants can remain after runner death. This is not adversarial containment. Audit external side effects before deliberately submitting again.

Adopted-child termination requires Linux pidfd support and permission; failures are explicit rather than falling back to PID-only signals. The current eight-job ten-minute soak bounds observed RSS/descriptors through daemon restarts and active backup/restore. It does not establish multi-day behavior, physical disk exhaustion, OOM or power-loss recovery.

- A machine reboot stops processes; persisted jobs are classified on restart, never promised to keep executing across shutdown. Fault injection covers vanished locks/stale boot identity and profile-specific log-write/log-sync/WAL-write ENOSPC. Physical volume exhaustion and power-loss VM tests remain pending.

- Runtime 0.1.14 flushes buffered log writes before synchronization, reporting write/flush/sync failure as a failed job where DB remains writable. If SQLite itself cannot commit due to disk/full/corruption, recovery may only classify unknown/orphaned; it preserves IDs and never replays native commands. There is no offline result journal. Runtime 0.1.10 and newer include consistent local database/log backups and new-profile restore; these do not guarantee recovery of a terminal commit that never reached SQLite.

- Default maximum eight active jobs; no waiting pool beyond this quota, tuning config, interactive stdin/PTY, schedules or artifacts. Runtime 0.1.12+ supports [pinned remote execution and workflow observation](remote-execution.md); arbitrary SSH processes remain local jobs.

## Logs, capacity and backups

- Published 0.1.17 keeps a 16-MiB prefix per stream. Runtime 0.1.18+ native exec/shell capture adds four recent 1-MiB segments after that prefix; evicted middle output and up to one pending MiB after abrupt runner loss can be unavailable. Remote observer copies and old runs retain prefix/tail limits. Text queries/exports use lossy UTF-8; byte cursors can split multibyte characters, and exports explicitly mark missing ranges. Runtime 0.1.10 and newer automatically compress eligible cold history/logs; archived history is retained indefinitely and no destructive purge is shipped.

- Every durable record is bounded by quotas but disk is not a reservation system. Schema v9 archives eligible jobs/targets/attempts without discarding history, preserves session identities and limits only live session registrations. Cold records, archived logs and historical inbox files still consume space. Dispatch permits four concurrent attempts across chats, with one live claim per logical destination. Four slow destinations can occupy all slots for their bounded three-second attempts. Idle cross-process completion discovery can take up to the one-second fallback interval before database/dispatch work; in-process writes wake workers immediately. Native gates and installed-package qualification are separate checks; see [implementation status](IMPLEMENTATION_STATUS.md).

Automatic data maintenance runs only while the daemon is running; it is not a system scheduler. Soft hot budgets cannot force archival of active work, unresolved deliveries or unexpired recoverable dead letters. The 10,000-job submission guard applies to hot history. Local daily backups retain three verified snapshots by default; they share the profile disk and need independent copying for disk-loss protection. Active output is a bounded prefix, not an atomic filesystem snapshot. Files outside managed database/log storage, host configuration and raw inbox receipt files are excluded. Linux/Windows maintenance behavior is tested; physical power-loss/ENOSPC and prolonged-load qualification remain open. See [data maintenance](data-maintenance.md).

## Inspection, monitoring and Web UI

The 0.1.12 structured progress interface adds bounded repeated stage/step/metric rules. It is a status channel with eight sources, 256 retained sample events, 128 progress alerts per job, per-rule cooldowns and one progress notification/second per job; suppressed matches are not delayed or replayed. Latest values and the last eight milestones persist, and terminal summaries may truncate with an explicit flag. The user confirms the real-Agent mid-run loop within the scope recorded in [live verification](live-e2e.md#real-agent-mid-run-feedback). Native Windows storage/progress checks pass on the published 0.1.12 baseline; installed checker workflows and additional host/version combinations need separate qualification. Source 0.1.17 goal feedback temporarily restores the original goal and requires native re-pause acknowledgement; group limits, deadlines and actual host acceptance are in [goal waiting](goal-waiting.md). See [the progress contract and checker](progress.md).

Runtime 0.1.10 and newer bundle a default-on authenticated loopback Web UI and runner-owned monitor rules. Linux/Windows native and installed-package checks pass. Literal/time rule revisions trigger once and must be explicitly rearmed; 16 rule identities and 128 revisions each bound retained configuration history. Their conditions are literal output matches, silence and elapsed time. Browser closing removes live visual feedback while durable alerts/local stops continue. Persisted observation timestamps can be stale after abrupt runner loss or storage contention; silence alone is not a hang diagnosis. Database write failure can prevent durable monitoring/control, and no new disk-loss journal is promised. See [runtime monitoring](runtime-monitoring.md).


## Installation, caches and upgrades

- Online ChatGPT Desktop/Codex entries require a global CLI. `ajr update` and `ajr uninstall` coordinate npm and the official Git marketplace through public host commands, preserving profiles/data and recording forward retries. Local/ZIP/modified/foreign catalogs keep their original routes. Active Linux runners survive only compatible online updates; native offline/Windows package replacement and incompatible migrations require finished jobs. Uninstall stops idle selected/default daemons; `--force` requires confirmed exact-run stops and local runner exit. Windows self-update/self-removal and actual Desktop refresh remain unqualified.

- Native installation/cache replacements have recorded forward repair. Setup/marketplace cross-file writes, native uninstall and pre-journal/legacy remnants may still need inspection. Only explicitly selected unchanged native caches are refreshed; host registry/enablement/removal remain host-owned. Source changes do not update installed files. Standalone MCP configuration supports Codex TOML and generic `mcpServers` JSON. No guessed ChatGPT settings, OS package/service or destructive purge is shipped. See [updates](updating.md) and [current loader/host evidence](live-e2e.md).

- The current local Codex bundle uses `.codex-plugin/plugin.json` and `.mcp.json` with an absolute installed native command. Cached MCP and terminal wrappers both need that managed installation to remain; historical native copies in new caches are not used by the launcher. Portable root MCP was not discovered and plugin-root command variables were not expanded by the tested CLI loader. Offline bootstrap is an explicit local development operation, not automatic host bootstrap or a directly installable marketplace ZIP (ADRs 0004/0007).

- Linux daemons spawn from the procfs self-executable link, so compatible existing runners survive image pathname replacement. Current runtime-starting entries replace an older daemon under the startup lock after pinned-peer and migration checks. Unverifiable removed legacy images fail before submission and need an explicit idle same-profile stop; no state switch or workload replay occurs.

Early 0.1.0 daemons without IPC shutdown can be stopped by the 0.1.2 client's verified Linux pidfd/SIGINT path. It requires proc access, pidfd support and a recognized `agent-job-relay` executable in daemon mode. Renamed binaries or failed identity/health checks are refused, with no force-kill fallback. Use the updated source executable with `daemon stop --install-root` to avoid an old installed launcher or wrong shell state; the real install still needs an explicit update.

## Distribution and qualification

- Source/offline delivery remains supported alongside published npm packages and the self-hosted marketplace. Offline hashes do not authenticate the publisher, declare a minimum libc version or download a build; use a trusted compatible Linux artifact. Old caches without the runtime profile need host refresh before managed cache refresh. Directory replacement journals permit checked forward repair; multi-directory/configuration updates remain separate and are not crash-atomic. The npm candidate includes native bytes and records minimum glibc; it uses no secondary native downloader or install hook. Published 0.1.15 passes manual OIDC publication and independent public-byte/channel/install/GitHub verification; published bytes must not be rebuilt or replaced. OpenCode V1 has an experimental packaged plugin verified with actual Bun name/version install and 1.19.4 interfaces through a loopback registry with a simulated model; real provider/restart/V2 checks remain open. Claude Code has an inbox-only source framework with synthetic helper/MCP-entry checks and no actual Claude account/loader test. Community tests and PRs are requested. Independent OS installers and package repositories are cancelled. Official directory submissions remain in TODO.md; subsequent preparation/publication runs remain maintainer-only and manually authorized.

## External execution (0.1.12+)

The reference command adapter needs the native executable and a persistent private profile on the remote host; custom scheduler adapters require separate implementation and qualification. Only external observers can automatically recover under the original local run lock. Remote identity mismatch, host loss, failed authentication or malformed responses provide no workload exit evidence. A local observation timeout ends as orphaned without stopping remote work; an unresolved control request can remain pending while disconnected. Remote native runner loss retains the existing unknown-effects boundary. The 16-MiB copied log prefix and bounded samples are not an artifact/checkpoint transfer service. GitHub Actions is read-only, fixes one attempt, has no workflow log stream and never dispatches/cancels/reruns. Current evidence and SSH/real-host notification limits are in [implementation status](IMPLEMENTATION_STATUS.md).

Native managed skills/MCP connections follow subsequent verified installation updates after a one-time migration/reconnection from historical full-skill/pre-forwarder entries. They cannot retrofit already running old binaries. Online pinned npm launchers still follow their matching release route. Dynamic catalog notification support depends on the host; the retained standard MCP regression is separate from real Desktop reload acceptance. Windows managed-update handoff remains unqualified. Missing/modified/downgraded/profile-moved installations fail explicitly; no global cache cleanup or unverified fallback occurs.
