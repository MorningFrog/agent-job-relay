# ADR 0007: offline plugin runtime and explicit cache lifecycle

Accepted, 2026-10-26, source 0.1.4. No personal installation, real host configuration or service is changed by development.

## Problem and evidence

The local plugin previously required a source build and manual update/cache work. A cached terminal launcher executed its own native copy while MCP used the original absolute installation, allowing versions to diverge. The source compatibility manifest also retained a stale version string. The official [package guide](https://developers.openai.com/plugins/build/plugins) and [desktop-only guide](https://developers.openai.com/plugins/deploy/desktop-only) describe portable packaging and a PLUGIN_ROOT placeholder. New isolated Codex CLI 0.164.0 probes still failed with the placeholder in stdio arguments and cwd, in addition to ADR 0004's command findings. Documentation support is not evidence this tested loader implements it.

## Decisions

- Keep one Rust executable. `plugin pack` exports an immutable local directory containing unbound templates, the authoring native image, license, shell launcher and a version/platform/SHA-256 manifest. It exports no chosen profile, configuration or credentials. This is a local development delivery artifact, not an OS installer or marketplace ZIP.
- The recipient invokes the moved bundle's `relay plugin bootstrap` with preview/apply. It validates layout and hashes, preflights installation/marketplace ownership, then installs the runtime and registers the local marketplace. No Rust/Python/Node toolchain is needed. Hashes are integrity checks, not publisher authentication; compatible libc and a trusted bundle remain requirements. No online fetching or automatic host hook is added.
- Existing installations retain the recorded state during plugin bootstrap/update regardless of shell state overrides; fresh bootstrap can select a custom state. Commands launched from a custom installed runtime default to that installation. Version metadata is rendered from the source/package version, and new management paths refuse downgrades. Same-version development updates are distinguished by file hashes.
- Both cached MCP and terminal launchers use the stable managed executable and pinned state. The installation must remain present; updating source or files does not change an already loaded process. Runtime replacement never stops a daemon and still refuses active locks/jobs. Reconnect MCP after updates.
- Installations carry a separate runtime snapshot profile with original installation/state/platform, version and file hashes. `plugin status`, `plugin update --cache` and `plugin cache refresh` inspect only explicitly supplied cache paths. Source and cache ownership are validated, unknown/modified/symlinked/missing/foreign/overlapping content is refused, and old snapshots are retained as backups. Host copies may include or omit the management receipt. Legacy copies without the new runtime profile require host refresh first.
- All selected caches are preflighted before an update changes the runtime. Install/source/cache locks fence cooperating lifecycle operations. Replacement uses staging and checked renames with restoration on a failed final rename; cross-directory install/marketplace/cache operations are not a crash transaction. Errors identify possible completed changes and the operation to retry. No implicit rollback after potential schema use, host enablement change, global cache scan, cache purge or state deletion is added.

Directory replacement interruption handling is superseded by [ADR 0008](0008-interrupted-plugin-replacement.md) in 0.1.5; cross-directory/configuration boundaries remain.

## Verification and remaining limits

Linux behavioral tests cover relocated/toolchain-free bootstrap, preview/idempotence, preserved database/marketplace bytes, multi-cache refresh with and without receipts, stale cached-native avoidance, actual daemon peer continuity during cache refresh, active update refusal, corrupt/incompatible/unsafe bundles, modified/foreign/legacy/symlinked caches, downgrade refusal, custom-root defaults and profile retention. Test artifact metadata can be altered deliberately to construct resource-only update/downgrade fixtures; that is not release provenance evidence.

The actual Codex loader check covers offline bundle relocation/bootstrap, marketplace installation, host-created cache/profile validation and MCP tool discovery in isolated HOME/CODEX_HOME, without a model turn or real ChatGPT Desktop endpoint. Current gate and live results are maintained in [implementation status](../IMPLEMENTATION_STATUS.md) and [live verification](../live-e2e.md). Browser installation, native non-Linux support, signed/downloaded artifacts and host-driven bootstrap retain their separate scope.
